## 中心思想

上一课改的是**行为**（技能），这一课改的是**知识的结构**——因为在大代码库里，**瓶颈不是"写"，而是"检索"**。

智能体读写执行的都是文件，而文件本质上是**非结构化**的。代码库越大，**找到该改哪个文件**就越难，也越费时间。现有的关键词搜索和正则匹配只认字面关键词，**把文件之间的关系全丢了**——修一个缓存问题，它能找到一部分该改的文件，却漏掉跟这些文件相关的另一些。

解法是**代码知识图谱**：一张属性图，用三种边把代码库连起来——**import**（文件引用文件）、**call**（函数调用函数）、**co-edit**（Git 历史里总被一起改动的文件）。检索时先用语义相似度找到**锚点**，再用 **PageRank** 沿边扩散打分。实测在 Django 仓库上省了 18% 的时间、17% 的步骤、16% 的 token。

## 核心要点

- **上一课和这一课的分工**：上一课教智能体新行为——把经验变成可复用技能。这一课看**另一种变强的方式**：**改变知识的组织方式**。
- **要看清的核心事实**：在大代码库里，**真正的瓶颈是检索，而不是代码生成**。
- **为什么**：编码智能体干活的常规方式是读、写、执行一大堆文件，而这些文件本质上是**非结构化的**——代码在文件里，文本也在文件里，两者都是松散的组织。
- **问题出在哪儿**：智能体在代码库上干得越久，代码库就越大。**往代码库里写不是问题**，真正的瓶颈是**检索和搜索**。**找到正确的、该修改的文件，是编码智能体最困难、也最耗时的任务之一。**
- **现在这套搜索方法的毛病**：它基于**正则表达式匹配**。关键词搜索或正则搜索的机制是找到与查询字面匹配的关键词，但它**丢掉了文件之间大量的关系**——尤其是在代码库上工作时。
- **一个例子**：假说要修代码库里的一个缓存问题。关键词搜索能找到一部分需要修改的文件，但**会漏掉另一些跟已找到文件有关系的文件**。
- **要建的东西——代码知识图谱（code knowledge graph）**：本质上是代码库的一张**属性图（property graph）**，带三种不同类型的关系：
  1. **import 关系（文件对文件）**：最基础的一种，是整张图的骨架，决定了智能体怎么从一个文件走到它依赖的所有东西。
     - 例子：有一个 Python 文件叫 `autoplay`，里面有两处 import，一处引自 `get_feed`，另一处引自 `rank_clip`。解析完之后，就得到 `autoplay` 与这两个来源之间的关系。
     - 如果 `get_feed.py` 发生了变化，`autoplay` 也可能受影响，因为它所依赖的那个文件的功能变了。
     - 把这种关系存进代码知识图谱，就是给编码智能体的提示：**该改什么、该去看什么**。
  2. **call 边（函数对函数）**：表示文件内部函数之间的关系。
     - 例子：`press_autoplay` 是 `autoplay` 这个 Python 文件里的一个函数，它在自己的 return 语句里调用了另外两个文件里的两个函数。
     - 解析完之后，就得到这些函数对函数的调用关系。这是给编码智能体的提示：**一旦改了 `get_clip` 或 `get_id` 这两个函数，就需要回头看看 `press_autoplay`**——因为它调用了这两个。
  3. **co-edit 边（文件对文件）**：存的是在代码库的 Git 历史里**总被一起改动**的那些文件。
     - 做法：分析提交历史，看哪些文件是被一起修改的，把这种关系存下来，为我们所用。
     - 解析之后，把 git log 的输入转成代码知识图谱的结构。这些文件就是给编码智能体的提示：**以后该被一起修改、一起查看**。
- **整张图长什么样**：它表示前面讲过的所有关系——co-edit、import 对 import、以及函数对函数的关系，全在代码库里。
- **检索之前要先清洗**：假设代码知识图谱里存在重复——有些文件本身就是彼此的副本，或者内容极其接近。需要**审计代码知识图谱、把这些节点去重**，把那些本来不该单独存在（因为跟别的太像）的节点去掉。做完这两步，图就可以用来检索了。
- **检索分两步**：
  1. **锚点（anchor）**：收到用户查询后，锚点是与这条查询有连接的第一个节点。锚点充当起始实体，编码智能体靠它、用**语义相似度**在图上找到开始搜索的节点，进而找到该修改的文件。
  2. **PageRank**：从锚点这个节点出发，沿图的边**一圈圈向外扩散**，给节点排名打分。
  这两步合起来，检索过程就完成了。
- **PageRank 好在哪里**：假设我们的仓库是个 TikTok 克隆，有一堆跟剪辑相关的功能，有一个 autoplay 按钮，我们想在这个代码库上干活。收到查询「怎么改进用于剪辑的 autoplay 按钮」时，PageRank 会遍历图，给出一份按重要度排序的节点列表——**分数同时取决于节点离锚点的距离，以及节点自身的语义相似度**。
- **为什么比朴素遍历强**：朴素遍历用的是**固定半径**——查询进来，走到锚点（跟查询最近的连接），然后返回结果。但离锚点同样远的每一个邻居，权重都**完全一样**；距离为二的那些邻居，权重也都一样。而 PageRank 给每个节点算的是一个**单独的分数**，是把这些因素综合起来得到的。
- **实测结果（Django 仓库上跑软件升级，用 Claude Code + Haiku 模型）**：
  - 四组：Claude Code 原样跑 / 给它代码知识图谱 / 给它锚点命中 / 给它随机文件当安慰剂。
  - **任务耗时改善 18%**，**到达第一次正确编辑所需的步数改善 17%**，**任务消耗的 token 减少 16%**。
  - 在 Django 仓库上跑 10 个不同任务，平均下来 **10 个里有 7 个**用代码知识图谱更快，**耗时中位数减少 11%**。
- **闭环怎么转**：新的提交进入代码库后，重新处理代码知识图谱——从新的提交里抽出新的边和连接；然后把它并进数据库；最后追加结果并重新排序。**这是一个自适应机制**，更新频率可以按使用场景自己决定：有些代码库需要很频繁地更新、要第一时间拿到最新知识；用得少的代码库，就可以把循环的频率降下来。

### 检索的两步：收到用户查询后，锚点是与这条查询有连接的第一个节点，它充当起始实体，编码智能体靠它在图上用语义相似度找到起点，进而找到该修改的文件；然后 PageRank 从锚点节点出发、沿图的边向外一圈圈扩散，给节点排名打分——这两步合起来，检索过程就完成了

> 现在我们进入实际的检索步骤。我们收到用户的查询，那么锚点就是与这条查询有连接的第一个节点。锚点会充当起始实体，编码智能体用它、通过语义相似度在图上找到开始搜索的节点，进而找到该修改的文件。然后 PageRank 会从锚点节点出发，沿着图的边一圈圈向上、向外扩散，给节点排名打分。这两步合在一起，检索过程就发生了。
> And now we go into the actual retrieval steps. We receive the user's query so the anchor is going to be the first node that has a connection with that query and the anchor will act as the starting entity that a coding agent will use to find with semantic similarity the starting node in the graph to search for the files to modify. And then PageRank will rank this in score along the edges of the graph starting from the anchors node and expanding in circles upward from that anchor. And these two steps together actually make the retrieval process happen.

### PageRank 举例：假设我们的仓库是个 TikTok 克隆，有很多跟剪辑相关的功能，有个 autoplay 按钮，我们要在这个代码库上干活；当收到「怎么改进用于剪辑的 autoplay 按钮」这条查询时，PageRank 会遍历图，给出一份按重要度排序的节点列表，分数同时取决于节点离锚点的距离和节点自身的语义相似度

> 这就是 PageRank 做的事。假设我们的仓库是个 TikTok 克隆，我们有很多跟剪辑相关的功能，有一个 autoplay 按钮，我们想在这个代码库上干活。现在假设我们从编码智能体那里收到一条查询：「怎么改进用于剪辑的 autoplay 按钮？」收到这条查询后，PageRank 会遍历图，给我们一份排好序的节点列表，这些节点的重要度和分数最高——分数取决于节点离锚点的距离，也取决于节点自身的语义相似度。
> This is what PageRank does. Let's assume that our repository is a tick-tock clone and we have lots of functionalities with clips, we have an autoplay button and we want to be able to work on this code base. Now let's say that we receive a query from the coding agent that says how do I improve the autoplay button for clipping? When this query is received, PageRank will traverse the graph and give us this sorted list of nodes with the highest importance and score based on the distance from the nodes as well as the semantic similarity in them.

### 为什么比朴素遍历强：朴素遍历用的是固定半径——查询进来、走到锚点（离查询最近的连接）、然后返回结果；但离锚点同样远的每个邻居权重都一样，距离为二的那些邻居权重也都一样；而 PageRank 给每个节点算的是把这些因素综合起来的定制分数

> 这比直接遍历更有效，因为朴素遍历用的是一条固定半径的查询：查询进来，走到锚点（也就是离查询最近的连接），然后返回结果。但离锚点同样远的每一个邻居，权重都会一样；距离为二的其他每一个邻居，权重也都会一样。而用了 PageRank，我们会拿到每个节点各自的分数，它是把这些因素综合起来算出来的。
> And this is more effective than direct traversal because plain traversal has a fixed radius query where the query comes in, it goes to the anchor which is the closest connection to the query and then returns the result. But every neighbor at the same distance from the anchor will have the same weight and every other neighbor at a distance of two will also have the same weight. However, with PageRank we will get a custom score for each one of the nodes based on a combination of these factors.

### 闭环怎么转：新的提交进入代码库后，我们从新提交里抽出新的边和连接、重新处理代码知识图谱，然后把它并进数据库，最后追加结果并重新排序；这是个自适应机制，更新频率可以按使用场景决定——需要最新知识的代码库更新得频繁，用得少的代码库就把循环频率降下来

> 现在我们想想怎么把闭环合上。新的提交进入代码库。我们会重新处理代码知识图谱，从新的提交里抽出新的边和新的连接。然后把它并进数据库，最后追加结果并重新排序。可以看到，这是一个自适应机制。我们可以根据自己面对的使用场景，来决定更新的频率。有些代码知识图谱更新得非常频繁，需要第一时间拿到大量更新后的知识。而对我们用得比较少的代码库，就可以把这个循环的频率降下来。
> Now let's think about closing the loop. A new commit comes into the code base. We will reprocess our code knowledge graph by extracting the new edges and the new connections from the new commits. Then we will merge this into the database and finally append and rerang the results. As you can see, this is an adaptive mechanism. We can decide on the frequency of the updates based on the type of use case we are working with. Or some code knowledge graphs that update very frequently and require a lot of this updated knowledge firsthand. We can reduce the frequency of the cycle and increase it for the code bases that we work on less.
