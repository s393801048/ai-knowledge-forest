## 中心思想

上一课讲清了"为什么"，这一课**亲手把它搭出来**：从 imports、函数调用、co-edits 三种关系构建代码知识图谱，再把基于图的检索和传统做法（正则匹配、文本搜索）放在一起比。

实测结论很干脆：**多跳问题上图检索赢**（目标文件离锚点超过一步时，关键词搜索找不到，图谱找得到），**简单问题上图谱也不吃亏**。把 PageRank 排出的文件提示注入 Claude Code 的 system prompt 之后，**任务效率整体提升约 10-12%**。

图谱还有一个别人比不了的优点：**追加成本几乎为零**——新增节点只需插一条边，不用整图重建。

## 核心要点

- **这一课动手做的事**：从 imports、函数调用、co-edits 构建代码知识图谱，并把基于图的检索跟传统做法（正则表达式匹配、文本搜索）作对比，看**结构化记忆在什么时候给 AI 智能体带来优势**。
- **节点与边**：节点是**文件**和**函数**，由三种关系连起来——文件对文件的 imports、函数对函数的 calls、文件对文件的 co-edits。节点带两个属性：**type**（是 file 还是 function）和 **label**（文件或函数的名字）。
- **存储结构**：因为边有起点（source）和终点（destination），所以**边是有方向的**。一张表存节点，另一张表存边和边的类型；然后在这两张表之上建一个**属性图（property graph）**，做法是告诉它"这张表放顶点、那张表放边"。
- **可视化怎么读**：**方块代表文件，三角代表函数**。绿点线是 co-edit；两个函数之间的 call 关系（比如 `cppr` 调用 `walkEdges`）是函数对函数；`api.py` 引自 `Retriever` 这种是 import，属于文件对文件。
- **遍历（traversal）怎么发生**：拿「在哪儿校验 token？」这个问题举例。AI 智能体看到查询后，通过代码知识图谱能推断出：锚点是 `verify_token`，因为它跟查询本身有语义相似度；然后从这个节点开始沿着图走。它相连的那些边**没有一条跟查询有语义相似度**，但我们照样能拿到这些信息——因为它跟那个文件之间的连接是**纯结构性的**，顺着知识图谱的结构就能走到。
- **改代码库时（增量）**：新增一个文件会产出新的节点，这些节点需要**追加**进代码知识图谱。这里的好处是——跟自适应智能体能做的其他适应方式相比，**追加成本几乎为零**。加完一个节点，这个函数和另一个函数之间就多了一条新关系，而插入的代价实际上接近于零；**我们不需要每追加一批新节点就把整张图重建一遍**。
- **真实代码库的规模**：作者自己的一个开源项目 **Agent Harness**（本身就是对 agent harness 的一个实现）。不再是几个节点几条边，而是 **208 个文件、约 1200 个符号、彼此之间 5000 多条边**（有些是重复的）。
- **图谱能省掉什么**：如果某个函数的信息没有被存在、保留在代码知识图谱里，智能体就没法又快又准地把这份信息取出来，它得**来回折腾很多轮工具调用**。有了图谱，这些引用关系就能直接给编码智能体用。
- **审计去重**：审计发现约 **4% 的重复节点，彼此相似度超过 96%**。这是多余的信息，还会制造重复的边。做法是把重复文件的**簇**找出来，把这些簇**一次性全部删掉**——它们不给图增加任何价值。这次只减掉了四个节点和几条边，影响不大。但**代码库越大、引用越多，这个问题就越严重**，需要持续盯着。
- **图上观察到的规律**：
  - 图里**大量是函数**——代码库的绝大部分由函数构成。**大多数函数不跟任何东西相连，因为它们是"原子"的**：不调用别的函数，所以没有任何引用。
  - 另有**一部分函数在一个"枢纽"里**：它们调用别的函数，并以某种方式连到文件上——**正是这一部分把整个实现连进了代码库的骨架**。
  - **文件层**里，要留意那些 import 边特别多的文件。**这些是关联最多的文件，度数最高，被别的文件引用得最多。** 因为它们天然带着大量的流量和连接，**我们必须特别小心地对待它们**——它们的实现会影响到跟它相连的任意多个文件（无论是文件对文件还是函数对函数）。
- **拿两类问题测效果**：
  1. **简单问题**：问题本身跟期望结果之间有**字面相似度**，编码智能体天然就能找到。
  2. **多跳问题**：相关节点和目标节点，在代码知识图谱里**离锚点超过一步**。
  - 多跳问题的例子：「`getChatArchive` 运行时，它调用的是哪个内部函数？」——**关键词搜索找不到它（找到的是另一个），而代码知识图谱找到了**，靠的是语义相似度搜索加上锚点系统。
  - 简单问题的例子里，查询本身就含字面相似的引用，所以字面相似度搜索和锚点系统都能找到。
- **结论**：总体上，**在多跳这类问题上用代码知识图谱是有收益的，在其他问题上也不会拖累编码智能体**——它只是帮智能体更快地找到正确的信息。
- **真实工作流里的实测做法**：让代码知识图谱被访问到——具体是**注入"哪些文件最相关"的提示**（按 PageRank 系统排好序），在解决代码库里的实现任务之前，把这些提示注入 **Claude Code 的 system prompt**。
- **在 httpie 上的结果**（用到两个 Anthropic 模型：**Sonnet 和 Haiku**）：综合起来整体表现提升约 **11%**。
  - 有一个反例：**那一簇理想文件没有被找到**。
  - 总体上：解决问题所需的 token **少了 3%**；到达解决方案所需的工具调用**少了 22%**；**快 36%** 到达对文件的第一次正确编辑；任务耗时**少了 10%**。
- **在 Django（更大的仓库）上的结果**：任务总耗时改善 **11%**；到第一次正确编辑的步数**减少 7%**；总 token 消耗**减少 5%**；成本**改善 6%**。
- **全部实验汇总**：把所有 10 个任务合在一起看，总体上在**所有任务上都是正收益**。比如其中一个是 base64 校验。
- **这一课的结论**：**让 AI 智能体把代码图谱用起来，能把任务效率提升约 10-12%。**

> 现在我们看看代码库被编辑时会发生什么。比如新增一个文件，随后它产出了节点，而这些节点需要被追加进代码知识图谱。这种情况下，拥有代码知识图谱的好处是：跟自适应 AI 智能体能做的其他类型的适应相比，**追加成本几乎为零**。加完一个节点之后，我们会看到这个函数和另一个函数之间有了一条新关系，但插入的成本实际上接近于零。而且我们不需要在每次追加新节点时，把整张代码知识图谱重新组织一遍。
