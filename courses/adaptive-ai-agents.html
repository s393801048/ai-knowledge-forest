全课主线

整门课解决的是智能体的一个致命短板：每次会话都从零开始。昨天花半小时踩明白的坑，今天开个新对话，还得再踩一遍——时间、token、还有"这次模型可能推出别的答案"的风险，全白付了。

解法是一把从便宜到贵的梯子。先在最便宜的token space（词元空间）动手：改行为、改知识，不用碰模型本身；这两招都用尽了还是不行，才爬到最贵的weight space（权重空间），动模型自己的参数。

问题：智能体没有记忆 → 每次运行都从零开始 → 重复踩坑，时间和 token 双输
  │
  ├─ 地基（分P 2）：先分清什么叫"记住"
  │    ├─ 智能体 = 模型 + 外壳（harness）；外壳负责组装上下文、跑工具、写记忆
  │    ├─ 四种记忆：工作记忆 / 情景记忆 / 语义记忆 / 程序性记忆
  │    └─ 长期记忆的原料 = 轨迹（trace）：对话、工具调用、决策、报错、修复
  │
  ├─ 第一层 · 行为适应（分P 3）→ 改【技能】
  │    ├─ 技能归纳管道：轨迹 → 归纳引擎起草 skill.md → 人工审核 → 进技能箱
  │    ├─ 关键设计：人在环上。批准=把提案变成行为；坏技能会天天重犯
  │    └─ 演示：run the tests 技能从 v1 升到 v2，测试全绿
  │
  ├─ 第二层 · 知识适应（分P 4-5）→ 改【检索】
  │    ├─ 诊断：大代码库里写不是瓶颈，【检索】才是
  │    ├─ 三种关系建成知识图谱：import（文件→文件）、call（函数→函数）、co-edit（Git 里一起改）
  │    ├─ 检索两步：锚点（语义相似度找到起点）→ PageRank（沿边扩散排序）
  │    ├─ 实测：多跳问题图检索赢，简单问题不吃亏；httpie 上省 22% 工具调用、36% 更快到第一次正确编辑
  │    └─ 闭环：新提交进来 → 抽新边 → 并库 → 重排，增量成本几乎为零
  │
  ├─ 第三层 · 模型适应（分P 6）→ 改【权重】
  │    ├─ 什么时候才用：拒答某话题、装人设、改语气格式——上下文改不动的行为
  │    ├─ 手段：LoRA 低秩适配（冻住原权重，只训两个小矩阵）+ 量化（32 位压到 4 位）
  │    ├─ 甜点区：训约 1% 的权重。太少学不会，太多【灾难性遗忘】
  │    └─ 演示：Qwen 0.6B + 礼貌 LoRA，14,000 组数据，训 1 小时，适配器只 150MB
  │
  └─ 收尾（分P 7）：行为 + 知识 + 权重，三层都掌握，智能体才会"越用越聪明"

中心思想

这门课解决智能体的一个致命短板：每次会话都从零开始。智能体会写代码、会用工具、能完成复杂任务，可它不记得昨天已经找到过的解法，于是同一个问题被反复重新解决一遍。

解法是给智能体装上"记住经验"的机制——不要把每次交互当成一次孤立的会话，而是让它把有用的信息留存下来，明天干得更好。课程具体带大家搭一个自适应编码智能体，它有两层适应机制：第一层行为适应，让智能体的技能随着运行越来越强；第二层知识适应，建一张代码知识图谱，让它记住代码里的主要关系。

这一集是全课的概念地图：先把"自适应智能体"这个词定义清楚，再讲明白遗忘到底贵在哪，最后给出该从哪儿下手的判断顺序。

核心是一个从便宜到贵的梯子。你要先问自己一句：更好的上下文和指令，能不能提升智能体的表现？ 能的话就走token space（词元空间）的两条路——让技能自己适应（第 3 课），或者用知识图谱搭自适应记忆（第 4-5 课）。这两条都走尽了还是不行，才轮到最贵的weight space（权重空间）：动模型本身（第 6 课）。

还有一个贯穿全课的关键区分：智能体 = 模型 + 外壳（harness）。模型只是推理的那股劲；真正组装上下文、跑工具、写记忆的是外壳。

核心要点

  • 今天的智能体会写代码、会用工具、能解复杂任务，但它经常重复犯同样的错，因为它不把经验带到下一次。
  • 这一课要建立三样东西：自适应 AI 智能体的心智模型、为什么遗忘很贵、智能体可以从哪些地方改进。
  • 周一 / 周二 / 周三的例子：
    • 周一：你让编码智能体跑 Python 测试，但 Python 解释器找不到项目里的某个模块。智能体去排查，发现了正确的项目命令，把测试跑通了。
    • 周二：你开了一个全新的对话，让它做一件很类似的事。因为没有周一的记忆，它又跑了错命令，又撞上同一个报错，再花时间和 token 去重新发现同一个修复方法。
    • 周三应该是不同的样子：我们希望它记得周一验证过的命令，直接从那开始，跳过周二浪费掉的时间和 token。
  • 遗忘的代价：没有记忆和学习，每一次重复的迭代，都是模型推出错误答案、多烧 token 的又一次机会。反过来，如果智能体从第一天的经验里学到了，第二天就会好得多，而且几乎不花钱。
  • 什么是智能体：一个能从环境里接收信息、用 LLM 推理下一步该做什么、并用工具作用于环境的系统。如果它有记忆，它还能把过去有用的经验留住。没有记忆，它可能完成今天的任务，但不会把学到的东西留到明天。
  • 智能体循环（agent loop）是怎么转的（用测试失败的例子）：
    1. 从用户请求开始——让智能体跑 Python 测试。
    2. 推理时，模型判断它需要检查项目仓库，于是向外壳（harness）申请一个工具。
    3. 外壳执行这个工具去检查项目，并把结果返回。
    4. 模型接着选择跑一条单独的测试命令，再申请一个工具、再跑一次，又返回一个错误。
    5. 模型的回复和工具结果（包括那个报错）都成为下一轮迭代的上下文历史。
    6. 如此重复，直到测试通过，或者智能体停下来。
  • 什么是外壳（harness）：LLM 是智能体的原始推理能力，外壳是它周围的软件脚手架。外壳负责组装模型看到的上下文、给模型访问和执行工具的能力、把结果记录进记忆、并在智能体循环里再次调用模型。模型加外壳，合起来才是一个能干活的智能体。
  • 记忆的四个类别：
    • 工作记忆（working memory）：此刻正在使用的消息和工具结果。
    • 情景记忆（episodic memory）：以前那些智能体运行里发生过的任何事。
    • 语义记忆（semantic memory）：项目相关的事实和知识。
    • 程序性记忆（procedural memory）：智能体学到的流程步骤。
  • 下一课聚焦程序性记忆：把经验变成可复用的技能。DeepLearning.AI 上一门关于"构建有记忆感知的智能体"的课深入讲过这部分，想了解更多可以去看看。
  • 长期记忆怎么建：从轨迹（trace）开始。轨迹就是一次智能体交互里每一个事件的完整记录。一个轨迹里包含：智能体干活时查看过的项目文件、为解决问题采取的动作、这些动作的结果、以及智能体做的修正。这些轨迹就是学习的原材料。
  • 该先在哪里下手：你要问的主要问题是——更好的上下文和指令，能不能提升智能体的表现？ 如果能，就用我们归为token space adaptation（词元空间适应）的两个主要手段：先建一个增强循环，让智能体的技能适应并变得更好；再用知识图谱搭一套自适应记忆。
  • 什么时候才轮到模型：如果这些手段都被用尽了，再没有什么能让智能体变得更好，那才去看模型本身在weight space（权重空间）里还有哪些可以增强的地方。这是最后一课的重点。

在学怎么改进智能体的学习方式之前，我们先简单把"智能体"这个词说清楚。智能体可以定义成一个这样的系统：它能从环境里接收信息，用 LLM 推理下一步该做什么，并用工具作用于环境。如果智能体有记忆，它还能把过去有用的经验留住。没有记忆，智能体可能完成今天的任务，但不会把学到的东西留到明天。 Before we learn about improving how agents can learn, let's briefly get clear on what we mean by an agent. An agent can be defined as a system that can take in information from its environment, reason about what to do next using an LLM, and use tools to act on its environment. If an agent has memory, it can also hold onto useful experience from the past. Without memory, the agent may complete today's task but won't retain what it's learned tomorrow.

我们用编码智能体测试失败这个例子，看看智能体循环是怎么转起来的。循环从一条用户请求开始，我们让智能体跑 Python 测试。推理期间，模型判断它需要检查项目仓库，于是向智能体外壳申请一个工具。外壳执行这个工具去检查项目，并把结果返回。模型接着选择跑一条单独的测试命令，再申请一个工具、再跑一次，又返回一个错误。模型的回复和工具结果（包括那个报错）随后都成为下一轮迭代的上下文历史的一部分。这个过程一直重复，直到测试通过，或者智能体停下来。 Let's use our coding agent's test failure example to see the agent loop in action. We start the loop with a user request, asking the agent to run our Python tests. During inference, the model decides it needs to inspect the project repository, so it requests a tool from the agent harness. The harness runs the tool to inspect the project and returns the result. The model then chooses to run a separate test command, requests another tool, runs it, and another error is returned. The model's responses and tool results, including the error, then become part of the context history for the next iteration. This repeats until the tests pass or the agent stops.

既然刚提到了"外壳（harness）"这个词，我们也把它拆开讲讲。LLM 是你智能体的原始推理能力。外壳是它周围的软件脚手架。它组装模型看到的上下文，给模型访问和执行工具的能力，把结果记录进记忆，并在智能体循环里再次调用模型。把模型和外壳放在一起，你就有了一个能干活的智能体。 Since we just used the word harness, let's also unpack that. The LLM is the raw reasoning power for your agent. The harness is the software scaffolding around it. It assembles the context the model sees, gives the model access and ability to run tools, records the results to memory, and calls the model again within the agent loop. Put the model and the harness together, and you have a working agent.

这一集讲第一层适应——行为层：把智能体留下的轨迹（trace）炼成可复用的技能，这样明天的智能体就不会重犯昨天的错。

具体做法叫技能归纳（skill induction）：归纳引擎用 LLM 读一批原始轨迹，起草一份简短的流程，写成 skill.md 文件；经人批准后，这份技能进入 skill box（技能箱），从此在每一个匹配的任务上被自动调用。因为批准等于把一份提案变成行为，坏技能一旦溜进去就会天天重犯、伤害不断累积，所以人必须留在环上。

核心要点

  • 这一课要做的事：把智能体的轨迹（过去的对话、工具调用、报错和修复）变成可复用的技能，这样明天的智能体就不会重犯昨天的错。
  • 什么叫技能归纳（skill induction）：拿原始轨迹——也就是智能体试过什么、在哪儿失败、最后什么管用的日志。归纳引擎（induction engine） 用 LLM 来审这些轨迹，起草一份简短的流程，形式是一个 skill.md 文件。然后经人批准，这份技能进入 skill box——一个受管的技能集合，供智能体取用。在这个过程里，我们把智能体的一次运行变成了别的智能体以后也能用的技能。
  • 怎么让技能持续变好（这是个循环）：
    1. 从 skill box 里已批准的技能出发。
    2. 智能体用这些技能去完成新任务，于是更多的轨迹堆积起来。
    3. 在智能体主管道之外，跑归纳引擎去读这些轨迹，提出「一份增强版技能 + 每一处改动的证据」。
    4. 人工审核：批准就升进 skill box 供智能体使用；驳回就给出理由，让归纳引擎下次能生成更好的增强提案。
  • 为什么必须有人在环上：想想批准这个动作实际做了什么——它把一份提案变成了行为。技能一旦被批准，从此在每一个匹配的任务上，智能体都会调用它。这是它的力量，也是它的风险。
    • 风险一：如果一个坏技能溜了过去，智能体就会每次都重犯这个错，伤害不断累积。
    • 风险二：轨迹是智能体从世界里收集来的数据。错误、甚至是被故意植入的指令，都可能被当成技能提出来。人工审核就是那道闸，挡住一条"毒轨迹"变成行为。
    • 附带好处：因为是人点下批准或驳回并给出理由，所以 skill box 里的每一份技能都有一个负责人，而每一次驳回都在教归纳引擎下次该修什么。
  • 演示里用到的两个开源包：Oracle Agent Memory（用来存轨迹）和 LangGraph + Oracle DB（用来跑技能归纳循环）。
  • 演示用的五份技能：brainstorming（头脑风暴）、requesting code review（请求代码评审）、run the tests（跑测试）、systematic debugging（系统性调试）、writing plans（写计划）。每份技能展示它的名字、主题、以及具体的流程。
  • 轨迹被拆成这几类内容：对话轮次（conversation turns）、工具调用（tool calls）、技能使用（skill uses）、流程步骤（workflow steps）、偏好（preferences）、以及报错和修复（errors and fixes）。
  • 归纳引擎的契约（contract）：也就是给 LLM 的指令。这份契约把同一个主题下的所有片段收拢起来，蒸馏成可复用的流程和经验教训，输出步骤、工具、报错、修复、以及任何需要的来源信息（provenance）。
  • 演示结果：引擎从轨迹里发现了一个反复出现的失败和对应的修法，据此提出了一份新的增强版技能，包含智能体可以照着做的四个步骤。人审通过后，run the test 的技能从 v1 升到 v2，设为 active。用同样的问题再跑一遍智能体，它加载了 v2，用上了改进后的流程，整个测试集全部通过。

智能体读写执行的都是文件，而文件本质上是非结构化的。代码库越大，找到该改哪个文件就越难，也越费时间。现有的关键词搜索和正则匹配只认字面关键词，把文件之间的关系全丢了——修一个缓存问题，它能找到一部分该改的文件，却漏掉跟这些文件相关的另一些。

解法是代码知识图谱：一张属性图，用三种边把代码库连起来——import（文件引用文件）、call（函数调用函数）、co-edit（Git 历史里总被一起改动的文件）。检索时先用语义相似度找到锚点，再用 PageRank 沿边扩散打分。实测在 Django 仓库上省了 18% 的时间、17% 的步骤、16% 的 token。

核心要点

  • 上一课和这一课的分工：上一课教智能体新行为——把经验变成可复用技能。这一课看另一种变强的方式：改变知识的组织方式。
  • 要看清的核心事实：在大代码库里，真正的瓶颈是检索，而不是代码生成。
  • 为什么：编码智能体干活的常规方式是读、写、执行一大堆文件，而这些文件本质上是非结构化的——代码在文件里，文本也在文件里，两者都是松散的组织。
  • 问题出在哪儿：智能体在代码库上干得越久，代码库就越大。往代码库里写不是问题，真正的瓶颈是检索和搜索。找到正确的、该修改的文件，是编码智能体最困难、也最耗时的任务之一。
  • 现在这套搜索方法的毛病：它基于正则表达式匹配。关键词搜索或正则搜索的机制是找到与查询字面匹配的关键词，但它丢掉了文件之间大量的关系——尤其是在代码库上工作时。
  • 一个例子：假说要修代码库里的一个缓存问题。关键词搜索能找到一部分需要修改的文件，但会漏掉另一些跟已找到文件有关系的文件。
  • 要建的东西——代码知识图谱（code knowledge graph）：本质上是代码库的一张属性图（property graph），带三种不同类型的关系：
    1. import 关系（文件对文件）：最基础的一种，是整张图的骨架，决定了智能体怎么从一个文件走到它依赖的所有东西。
      • 例子：有一个 Python 文件叫 autoplay，里面有两处 import，一处引自 get_feed，另一处引自 rank_clip。解析完之后，就得到 autoplay 与这两个来源之间的关系。
      • 如果 get_feed.py 发生了变化，autoplay 也可能受影响，因为它所依赖的那个文件的功能变了。
      • 把这种关系存进代码知识图谱，就是给编码智能体的提示：该改什么、该去看什么。
    2. call 边（函数对函数）：表示文件内部函数之间的关系。
      • 例子：press_autoplay 是 autoplay 这个 Python 文件里的一个函数，它在自己的 return 语句里调用了另外两个文件里的两个函数。
      • 解析完之后，就得到这些函数对函数的调用关系。这是给编码智能体的提示：一旦改了 get_clip 或 get_id 这两个函数，就需要回头看看 press_autoplay——因为它调用了这两个。
    3. co-edit 边（文件对文件）：存的是在代码库的 Git 历史里总被一起改动的那些文件。
      • 做法：分析提交历史，看哪些文件是被一起修改的，把这种关系存下来，为我们所用。
      • 解析之后，把 git log 的输入转成代码知识图谱的结构。这些文件就是给编码智能体的提示：以后该被一起修改、一起查看。
  • 整张图长什么样：它表示前面讲过的所有关系——co-edit、import 对 import、以及函数对函数的关系，全在代码库里。
  • 检索之前要先清洗：假设代码知识图谱里存在重复——有些文件本身就是彼此的副本，或者内容极其接近。需要审计代码知识图谱、把这些节点去重，把那些本来不该单独存在（因为跟别的太像）的节点去掉。做完这两步，图就可以用来检索了。
  • 检索分两步：
    1. 锚点（anchor）：收到用户查询后，锚点是与这条查询有连接的第一个节点。锚点充当起始实体，编码智能体靠它、用语义相似度在图上找到开始搜索的节点，进而找到该修改的文件。
    2. PageRank：从锚点这个节点出发，沿图的边一圈圈向外扩散，给节点排名打分。

这两步合起来，检索过程就完成了。

  • PageRank 好在哪里：假设我们的仓库是个 TikTok 克隆，有一堆跟剪辑相关的功能，有一个 autoplay 按钮，我们想在这个代码库上干活。收到查询「怎么改进用于剪辑的 autoplay 按钮」时，PageRank 会遍历图，给出一份按重要度排序的节点列表——分数同时取决于节点离锚点的距离，以及节点自身的语义相似度。
  • 为什么比朴素遍历强：朴素遍历用的是固定半径——查询进来，走到锚点（跟查询最近的连接），然后返回结果。但离锚点同样远的每一个邻居，权重都完全一样；距离为二的那些邻居，权重也都一样。而 PageRank 给每个节点算的是一个单独的分数，是把这些因素综合起来得到的。
  • 实测结果（Django 仓库上跑软件升级，用 Claude Code + Haiku 模型）：
    • 四组：Claude Code 原样跑 / 给它代码知识图谱 / 给它锚点命中 / 给它随机文件当安慰剂。
    • 任务耗时改善 18%，到达第一次正确编辑所需的步数改善 17%，任务消耗的 token 减少 16%。
    • 在 Django 仓库上跑 10 个不同任务，平均下来 10 个里有 7 个用代码知识图谱更快，耗时中位数减少 11%。
  • 闭环怎么转：新的提交进入代码库后，重新处理代码知识图谱——从新的提交里抽出新的边和连接；然后把它并进数据库；最后追加结果并重新排序。这是一个自适应机制，更新频率可以按使用场景自己决定：有些代码库需要很频繁地更新、要第一时间拿到最新知识；用得少的代码库，就可以把循环的频率降下来。

检索的两步：收到用户查询后，锚点是与这条查询有连接的第一个节点，它充当起始实体，编码智能体靠它在图上用语义相似度找到起点，进而找到该修改的文件；然后 PageRank 从锚点节点出发、沿图的边向外一圈圈扩散，给节点排名打分——这两步合起来，检索过程就完成了

现在我们进入实际的检索步骤。我们收到用户的查询，那么锚点就是与这条查询有连接的第一个节点。锚点会充当起始实体，编码智能体用它、通过语义相似度在图上找到开始搜索的节点，进而找到该修改的文件。然后 PageRank 会从锚点节点出发，沿着图的边一圈圈向上、向外扩散，给节点排名打分。这两步合在一起，检索过程就发生了。 And now we go into the actual retrieval steps. PageRank 举例：假设我们的仓库是个 TikTok 克隆，有很多跟剪辑相关的功能，有个 autoplay 按钮，我们要在这个代码库上干活；当收到「怎么改进用于剪辑的 autoplay 按钮」这条查询时，PageRank 会遍历图，给出一份按重要度排序的节点列表，分数同时取决于节点离锚点的距离和节点自身的语义相似度

这就是 PageRank 做的事。假设我们的仓库是个 TikTok 克隆，我们有很多跟剪辑相关的功能，有一个 autoplay 按钮，我们想在这个代码库上干活。现在假设我们从编码智能体那里收到一条查询：「怎么改进用于剪辑的 autoplay 按钮？」收到这条查询后，PageRank 会遍历图，给我们一份排好序的节点列表，这些节点的重要度和分数最高——分数取决于节点离锚点的距离，也取决于节点自身的语义相似度。 This is what PageRank does. When this query is received, PageRank will traverse the graph and give us this sorted list of nodes with the highest importance and score based on the distance from the nodes as well as the semantic similarity in them.

为什么比朴素遍历强：朴素遍历用的是固定半径——查询进来、走到锚点（离查询最近的连接）、然后返回结果；但离锚点同样远的每个邻居权重都一样，距离为二的那些邻居权重也都一样；而 PageRank 给每个节点算的是把这些因素综合起来的定制分数

这比直接遍历更有效，因为朴素遍历用的是一条固定半径的查询：查询进来，走到锚点（也就是离查询最近的连接），然后返回结果。但离锚点同样远的每一个邻居，权重都会一样；距离为二的其他每一个邻居，权重也都会一样。而用了 PageRank，我们会拿到每个节点各自的分数，它是把这些因素综合起来算出来的。 And this is more effective than direct traversal because plain traversal has a fixed radius query where the query comes in, it goes to the anchor which is the closest connection to the query and then returns the result. But every neighbor at the same distance from the anchor will have the same weight and every other neighbor at a distance of two will also have the same weight. However, with PageRank we will get a custom score for each one of the nodes based on a combination of these factors.

  • 节点与边：节点是文件和函数，由三种关系连起来——文件对文件的 imports、函数对函数的 calls、文件对文件的 co-edits。节点带两个属性：type（是 file 还是 function）和 label（文件或函数的名字）。
  • 存储结构：因为边有起点（source）和终点（destination），所以边是有方向的。一张表存节点，另一张表存边和边的类型；然后在这两张表之上建一个属性图（property graph），做法是告诉它"这张表放顶点、那张表放边"。
  • 可视化怎么读：方块代表文件，三角代表函数。绿点线是 co-edit；两个函数之间的 call 关系（比如 cppr 调用 walkEdges）是函数对函数；api.py 引自 Retriever 这种是 import，属于文件对文件。
  • 遍历（traversal）怎么发生：拿「在哪儿校验 token？」这个问题举例。AI 智能体看到查询后，通过代码知识图谱能推断出：锚点是 verify_token，因为它跟查询本身有语义相似度；然后从这个节点开始沿着图走。它相连的那些边没有一条跟查询有语义相似度，但我们照样能拿到这些信息——因为它跟那个文件之间的连接是纯结构性的，顺着知识图谱的结构就能走到。
  • 改代码库时（增量）：新增一个文件会产出新的节点，这些节点需要追加进代码知识图谱。这里的好处是——跟自适应智能体能做的其他适应方式相比，追加成本几乎为零。加完一个节点，这个函数和另一个函数之间就多了一条新关系，而插入的代价实际上接近于零；我们不需要每追加一批新节点就把整张图重建一遍。
  • 真实代码库的规模：作者自己的一个开源项目 Agent Harness（本身就是对 agent harness 的一个实现）。不再是几个节点几条边，而是 208 个文件、约 1200 个符号、彼此之间 5000 多条边（有些是重复的）。
  • 图谱能省掉什么：如果某个函数的信息没有被存在、保留在代码知识图谱里，智能体就没法又快又准地把这份信息取出来，它得来回折腾很多轮工具调用。有了图谱，这些引用关系就能直接给编码智能体用。

核心要点

  • 这一课的定位：前面你改进智能体时都没有动模型本身。这一课进入weight space adaptation（权重空间适应），看微调（fine-tuning）这类技术怎么用、什么时候用。
  • 三层各自的长处：
    • 行为适应（第 2 课）：一种成本非常友好的方式，让智能体用自己已有的数据持续变强。
    • 知识适应（第 3、4 课）：当智能体取到错误数据时，代码知识图谱能提供极大帮助。
    • 权重适应：可能被认为是一种昂贵的改造智能体行为的方式，但在某些情况下，当我们想要的适应达不到时，这个选项仍然在手——而且是别的方案大概做不到的。
  • 一条重要的反例：因为基础模型是在整个互联网上训练的，通过改动权重给模型添加新信息，通常是个坏决定。
  • 权重修改能达到两个主要目的：
    1. 拒答（refusing）：比如拒绝回答关于某个话题或某个人的问题。
    2. 格式化或调整行为（formatting / adapting behaviors）：比如做一个微调模型，让它说话更礼貌，或者在回答问题时贴合某个特定的品牌口吻或风格。
  • 怎么做到的：把原来神经网络的权重冻结或保存下来，然后在它上面加一个小小的附加件。这正是微调的实际用途：模型已经训好之后，去打补丁修补某些具体行为。
  • 多个适配器怎么协作：当你用不同行为微调出好几个适配器之后，可以有一个路由（router），从训练好的列表里挑最合适的那个适配器，根据输入去响应不同的任务。
  • LoRA 是什么：LoRA 的全称是低秩适配（low-rank adaptation），是微调时非常常用的一种技术。模型有权重、有神经元、有代表神经元的那些数值。LoRA 做的事情是：把原来神经网络的权重冻结或复制一份，然后加上两个小矩阵，它们携带一份 bias，会被加到一部分神经元上。这两个矩阵就是我们要训练的全部。
  • LoRA 的公式：保留原来的权重，叫 W，然后在它之上加一小块训练出来的修正，用 B 和 A 表示。公式里的那个乘数，代表这个行为改变要施加得多强。
  • 训练多少：在模型所有参数里，我们的目标是训大约 1%。要记住，做微调的时候，我们实际上是在覆盖神经元原来的数值——训太多会出问题，训太少也会出别的问题。
  • 一个关于"快乐"的类比：想象我们有很多表达快乐的提示词，让一个 AI 智能体去读。因为模型读了这些提示，它在读到"快乐"（或者从 embedding、从表示的角度看，读到"快乐的近似物"）时，不同的神经元部位会被激活。一个用微调训出来的适配器，会把给到它的所有神经元里的快乐都观察一遍，把它们写进一条可以分析的残差流（residual stream）。有了这张"用到快乐时被激活的所有神经元"的残差图，我们就能把 B 和 A 这两个矩阵作为原模型上的附加件训练出来。
  • 这两个矩阵干什么：
    • 第一个：读上下文，先决定在回答里把快乐"点火"点得多强。比如用户说「嘿，希望你今天过得不错」，那么适配器就更可能用快乐的方式回答。
    • 第二个：把这种行为写进一个低维矩阵，用来承载"快乐"这份 bias。
  • 甜点区问题：一个模型应该被改造或重训多大比例？这里有两个主要问题：
    • 训得太少：我们想训的行为大概学不会，因为区分这个新行为的神经元太少了。
    • 训得太多：会造成灾难性遗忘（catastrophic forgetting）——你实际上覆盖掉了那个原本训练得非常强大的神经网络的权重。
    • 黄金点通常是模型权重的 1% 左右（针对 LoRA 这种低秩适配技术）。理想情况下，用最少的权重，换到最大的行为改变。
  • 演示：礼貌版 Qwen：一个 4 位量化的 LoRA 适配器，套在 Qwen 上面，训练方式就是喂给它大量的礼貌文本样本。
    • 比如提示「怎么在 Python 里反转一个字符串？」——原来那个底座模型会给你一个很朴素的回答；而新版会给你一个非常热情、非常恭维的回答。
  • 对比结果：拿「怎么在 Python 里读一个文件？」去问底座模型（Qwen 的 6 亿参数模型），返回的是个正常的回答。而训出来的 LoRA 适配器（礼貌版）回答得极其客气、极其殷勤。
  • 体积上的权衡：原来的模型总共重 4GB，基础模型总共重 5GB，而训练出来的适配器只有大约 150MB。也就是说，只重训大约 4% 到 5% 的权重，就实现了这个行为上的改变。
  • 训练数据：超级礼貌版 Qwen 是一次 LoRA 微调，用的是一些礼貌的问答对——大约 14,000 组合成生成的"问题 + 礼貌回答"。我们可以造出尽可能多样的例子，配上真正礼貌的答案。然后把这些信息用不同强度的语气（比如 gorgeous、warm、effusive）喂给底座模型，再训练 LoRA 适配器，微调就完成了。
  • 量化（quantization）：训练时我们用了量化。做法是把神经元的权重数值从 32 位浮点压成 4 位。4 位能表示 2 的 4 次方、也就是 16 个可能的取值，所以把浮点值缩放到 0 到 15 之间。反过来把 4 位还原成 32 位时，得到的值跟原来会略有不同——因为我们把 32 位塞进 4 位再变回来，引入了重建误差。代价是损失一点精度，回报是能用更少的位数把这些数存下来。
  • 量化对存储的意义：这个 6 亿参数的模型加载起来只占大约 1GB 内存。之所以能做到，是因为我们把权重值量化成了 4 位；否则它需要多得多的存储空间。
  • 推理时怎么用：训练完适配器后，我们拿到 A 和 B 这两个矩阵，它们承载着"礼貌"的数值。每次做推理时，把这些 bias 加到神经网络原来的权重上。
  • 训练成本：这个适配器训了1 小时，很轻松地就把训练损失降到了一个可接受的值。
  • 微调为什么贵：模型越大，微调这件事通常要交给云服务商来做，因为大模型微调需要的资源量非常大——要把所有神经元的权重和别的东西都载入内存，有些普通硬件根本扛不住。为了演示微调确实可以做，作者自己微调了这个适配器。
  • 训练统计：训练实际花了1 小时，模型是 6 亿参数。作个参照，这大约只是一个前沿实验室（Frontier Lab）模型实际参数量的 0.1% 到 0.01%。所以如果你要微调一个具备前沿能力的模型，就得在多种资源上跑几百甚至几千小时。
  • 这次训了多少：最终训了大约 5% 的权重——这是把"超级礼貌"这个人设装进 Qwen 所必需的权重改写量。
  • 上生产环境：你会有一个系统实时处理用户查询，然后决定让训好的哪个适配器来接手回答。
    • 问题在于：前面那条查询是技术性的，用户真正需要的是事实性回答，而不是礼貌回答。
    • 所以最好能有一个环节或系统，在把用户的提示发给底座模型或礼貌模型之前，先决定由哪个模型来回答。
  • 路由（router）：为此做了一个路由模块，基于一些正则表达式匹配，从这些模式里判断该把问题路由到某一个可用的适配器，还是落到底座模型本身。
    • 比如在谈单元测试的场景里，如果正则匹配器判断用户需要回答里多一点温度，那么超级礼貌适配器就会加到基础模型上，由它来回答。
    • 而在另一种情况下——路由检测到用户只需要一个事实性回答——就会改为加载基础模型，用户查询通过基础模型、不带任何适配器来回答。
  • 实际能用来做什么：避免回答某一类问题、拒绝谈论敏感话题、适配特定的语气或格式，以及很多其他例子。

甜点区问题：一个模型该被改造或重训多大比例？训得太少，想训的行为大概学不会，因为区分这个新行为的神经元太少；训得太多，会造成灾难性遗忘，把原来训练得非常强大的权重覆盖掉；对 LoRA 这种低秩适配技术来说，黄金点通常是权重的 1% 左右——理想情况是用最少的权重换到最大的行为改变

我们面对的问题是：一个模型应该被改造或重训多大比例？这里有两个主要问题。如果我们训的权重太少，那我们想训的行为大概学不会，因为区分这个新行为的神经元太少了。还有另一个问题，就是训得太多。这会导致所谓的灾难性遗忘，因为你实际上覆盖掉了那个原本训练得非常强大的神经网络的权重。所以对低秩适配这种技术来说，黄金点通常是权重的 1% 左右。理想情况下，我们想用最少的权重，换到最大的行为改变。 We are confronted with this question of how much percentage of a model should be adapted or retrained. So there are two main problems. There's another problem, which is training too many. And this causes being called catastrophic forgetting because you actually overwrite the weights of the neural network that was trained so powerfully. So the golden point is typically around 1% of the weights for this low rank adaptation technique. Ideally, we want to train the lowest amount of weights that give us the most amount of behavior change.
